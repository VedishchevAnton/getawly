# Getawly: подготовка к боевому запуску

Дата: 2026-09-23

## Задача

Проект работает локально, но конфигурация целиком dev-овая: секреты лежат в
репозитории, база открыта наружу, токены Telegram-ботов владельцев хранятся
открытым текстом, HTTPS нет, состояние бота живёт в памяти процесса. Нужно
довести проект до состояния, в котором его можно развернуть на боевом сервере
с реальными клиентами.

### Контекст и ограничения

Согласовано с заказчиком:

- **Хостинг** — VPS с Docker Compose. TLS терминируем сами, Postgres и Redis
  остаются в контейнерах, секреты подаются файлом `.env` на сервере.
- **Стадия** — рабочей версии с боевыми данными нет, всё только локально.
  Схему можно менять свободно, миграция существующих данных не требуется.
- **Тесты** — тестовой инфраструктуры в проекте нет, заводим в рамках этой
  задачи, включая тесты ключевых эндпоинтов.
- **Главный критерий** — «чисто, просто, лаконично». При выборе между
  функциональностью и простотой выигрывает простота.

### Критерий успеха

Проект разворачивается на чистом VPS командой `docker compose -f
docker-compose.yml -f docker-compose.prod.yml up -d` при наличии заполненного
`.env` и A-записи домена. Приложение недоступно, если конфигурация небезопасна.
`docker compose up` без аргументов по-прежнему поднимает рабочий dev-контур.

## Решения

### Топология

Один `deploy/Caddyfile` на оба контура — Caddy подставляет переменные окружения
со значением по умолчанию:

```caddyfile
{$SITE_ADDRESS:http://localhost:8088} {
    encode gzip
    handle_path /media/* {
        root * /var/www/uploads
        file_server
    }
    reverse_proxy api:8000
}
```

Переменная не задана — Caddy слушает `:8088` без TLS, как сейчас работает dev.
На проде `SITE_ADDRESS=getawly.ru` включает автоматический выпуск и продление
сертификата Let's Encrypt, редирект http→https и HSTS. Директива `handle_path`
срезает префикс `/media`, повторяя поведение `alias` в прежнем nginx-конфиге.

`docker-compose.yml` остаётся dev-конфигом. `docker-compose.prod.yml` —
override, который меняет ровно четыре вещи: порты Caddy на 80/443, том под
сертификаты, убирает проброс 5432 у Postgres и делает пароль базы обязательным
через `${POSTGRES_PASSWORD:?...}` — Compose откажется стартовать с внятной
ошибкой, если переменной нет.

Сервисы: `postgres`, `redis`, `migrate`, `api`, `caddy`.

Caddy получает именованный том `caddy_data` для сертификатов. Без него
контейнер перевыпускает сертификат на каждом рестарте и упирается в лимиты
Let's Encrypt.

**Почему Caddy, а не nginx + certbot.** Автоматический TLS убирает из системы
контейнер certbot, два общих тома, петлю автопродления и reload nginx после
обновления — четыре движущиеся части против нуля. Прежний `deploy/nginx.conf`
занимал 16 строк и делал две вещи, накопленной настройки, которую жалко
терять, в проекте нет.

### Конфигурация и секреты

В `Settings` добавляются `redis_url` и `encryption_key`, и появляется
`model_validator(mode="after")`. При `APP_ENV=production` старт падает, если:

- `SECRET_KEY` равен дефолтному `dev-insecure-change-me` или короче 32 символов;
- `ENCRYPTION_KEY` не задан.

Ошибка конфигурации обнаруживается в момент деплоя, а не через месяц после
утечки. В dev-режиме валидация не срабатывает и быстрый старт продолжает
работать без заполнения `.env`.

Пароль Postgres уходит из `docker-compose.yml` в переменную окружения. В
dev-конфиге у неё остаётся значение по умолчанию (`${POSTGRES_PASSWORD:-getawly}`)
ради быстрого старта, в прод-override значения по умолчанию нет.

### Шифрование токенов ботов

Новый модуль `app/crypto.py`:

- `EncryptedString(TypeDecorator)` на базе Fernet — шифрует при записи,
  расшифровывает при чтении. Прозрачен для вызывающего кода.
- `token_hash(value)` — HMAC-SHA256 для колонки с уникальным индексом.

Ключ берётся из `ENCRYPTION_KEY`. Если переменная не задана (только dev), ключ
детерминированно выводится из `SECRET_KEY`, поэтому локальный запуск не требует
дополнительной настройки. В проде валидатор настроек требует явного ключа.

В модели `Owner` меняется одна строка:

```python
bot_token: Mapped[Optional[str]] = mapped_column(EncryptedString(512), nullable=True)
bot_token_hash: Mapped[Optional[str]] = mapped_column(String(64), nullable=True, unique=True)
```

Два следствия, которые обрабатываются явно:

- **Длина.** Шифротекст Fernet для токена BotFather не помещается в `String(128)`,
  колонка расширяется до 512.
- **Уникальность.** Fernet недетерминирован, поэтому `unique=True` на
  зашифрованной колонке бесполезен: один и тот же токен даст разный шифротекст.
  Уникальность переносится на `bot_token_hash`. Это не косметика — без неё два
  владельца смогут завести один и тот же бот и будут перебивать друг другу
  вебхук.

`bot_token` нигде не участвует в `WHERE` — его только читают у загруженного
`Owner` (`app/services/bot_runtime.py`, `app/api/cabinet.py`), поэтому
прозрачное шифрование не ломает ни одного запроса.

Хеш заполняется там же, где присваивается сам токен — в обработчике
`app/api/cabinet.py`: `owner.bot_token = token` и
`owner.bot_token_hash = token_hash(token)` идут рядом. Отдельный слой или
событие SQLAlchemy для одной точки записи были бы лишними.

В зависимости добавляется `cryptography` — Fernet живёт там. Сейчас пакет в
`pyproject.toml` не объявлен.

Миграция `002` меняет тип колонки и добавляет `bot_token_hash` с индексом,
снимая прежнее ограничение уникальности. Backfill не нужен — боевых данных нет.

### Миграции при старте

Одноразовый сервис `migrate` выполняет `alembic upgrade head` и завершается;
`api` стартует через `depends_on: condition: service_completed_successfully`.
Это убирает гонку, при которой несколько реплик накатывают миграции
одновременно.

Из `Dockerfile` alembic уходит, `CMD` сводится к запуску uvicorn, создание
`uploads` переезжает в слой `RUN`. Файл `scripts/entrypoint.sh` удаляется — он
дублирует `CMD` и после этой правки не используется.

### Redis

Сервис `redis:7-alpine` без проброса портов, с healthcheck по `redis-cli ping`.
`app/bot/storage.py` переходит на `RedisStorage.from_url(settings.redis_url)` —
в файле уже стоит комментарий, что так и планировалось. FSM-состояния перестают
теряться при рестарте контейнера, и появляется возможность запустить несколько
воркеров.

Кэш инстансов ботов (`_cache` в `bot_runtime.py`) остаётся в памяти процесса:
там лежат объекты `Bot`, а не состояние диалога, и каждый воркер спокойно
построит свой.

### Бэкапы

`scripts/backup.sh` запускается на хосте: `pg_dump` через `docker compose exec`,
сжатие gzip, файл `./backups/getawly-<дата>.sql.gz`, удаление файлов старше
14 дней. В README добавляется строка для host cron.

Отдельный контейнер-шедулер не заводим: он добавляет движущуюся часть, отказ
которой легко не заметить, а выигрыша при одном сервере не даёт.

### Тесты

В dev-зависимости добавляются `pytest`, `pytest-asyncio`, `httpx`. Тесты идут
против отдельной базы `getawly_test`; фикстура подменяет зависимость `get_db`.

| Файл | Что покрывает |
|------|---------------|
| `test_crypto.py` | round-trip шифрования, отлуп подменённого шифротекста, детерминизм хеша |
| `test_config.py` | прод-валидация отвергает дефолтный `SECRET_KEY` и отсутствующий `ENCRYPTION_KEY` |
| `test_auth.py` | регистрация, логин, повторный email |
| `test_units.py` | создание объекта требует авторизации, чужой объект недоступен |

## Вне объёма

- **S3 для загрузок.** На одном VPS локальный том плюс бэкап решают ту же
  задачу, а S3 тянет за собой креды, клиент и миграцию путей.
- **Вынос кэша ботов в Redis.** См. раздел Redis.
- **CI-пайплайн.** Не запрашивался.
- **Эндпоинт загрузки фотографий.** В API его сейчас нет совсем (`UploadFile`
  не используется). Это отдельная функциональность, а не проблема
  production-готовности.
