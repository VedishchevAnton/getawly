# Getawly: подписка, оплата и замыкание сценария заявок

Дата: 2026-09-23

## Задача

Продуктовый сценарий из README описан так: хозяин регистрируется, подключает
своего бота, заполняет объекты, оплачивает подписку и работает. Сверка с кодом
показала, что цепочка разорвана в трёх местах, и одно из них принципиальное.

### Что уже работает

Регистрация с выдачей триала, подключение бота от BotFather с установкой
вебхука, управление объектами и календарём, полный сценарий гостя в боте
(`/start` → даты → выбор объекта → заявка) с корректной проверкой занятости по
бронированиям и ручным блокировкам.

### Что разорвано

1. **Оплаты нет вообще.** Страница подписки сообщает, что ЮKassa подключится
   позже. Цена нигде не задана, `yookassa_shop_id` и `yookassa_secret_key`
   пустые.
2. **Подписка ни на что не влияет.** `subscription_is_usable` вызывается ровно
   дважды, и оба раза — для вывода статуса в кабинете. Ни бот, ни приём заявок
   её не проверяют: после конца триала всё продолжает работать. Монетизации нет
   не потому, что нет приёма денег, а потому, что неоплата ничего не
   ограничивает.
3. **Хозяин не узнаёт о заявке.** Гостю отвечают «Заявка отправлена хозяину», но
   `create_booking` только пишет в базу. Заявку видно, лишь если самому открыть
   кабинет.
4. **Фото объекта загрузить нечем.** Модель `UnitPhoto`, том `uploads` и раздача
   через `/media/` готовы, но в API нет ни одного `UploadFile`.

### Условия, согласованные с заказчиком

- Тариф — **100 ₽ за 30 дней**, единый, без градаций по числу объектов.
- Триал — **один месяц** (сейчас в конфиге 14 дней, меняется на 30).
- Оплата реализуется по-настоящему: рабочий провайдер ЮKassa плюс заглушка для
  локальной разработки.
- Проект на раннем этапе, боевых данных нет — схему можно менять свободно.
- Критерий качества — «чисто, просто, лаконично».

### Критерий успеха

Хозяин проходит путь целиком без ручного вмешательства в базу: регистрация →
подключение бота → объекты → месяц бесплатно → оплата 100 ₽ → продление. После
истечения оплаченного периода бот перестаёт принимать заявки, а кабинет
остаётся доступен. О каждой новой заявке хозяин узнаёт из своего бота и может
ответить на неё оттуда же.

## Решения

### Подписка и оплата

В конфигурацию добавляются `subscription_price_rub = 100`,
`subscription_period_days = 30`, `payment_provider = "stub"`, и `trial_days`
меняется с 14 на 30.

Новая таблица `payments`: сумма, валюта, статус (`pending` / `succeeded` /
`failed`), имя провайдера, внешний идентификатор платежа, `created_at`,
`paid_at`, ссылка на владельца. Журнал нужен независимо от провайдера — без
него нельзя ни свериться с выпиской, ни разобрать спор с клиентом.

Провайдер скрыт за протоколом в `app/services/payments.py`:

```python
class PaymentProvider(Protocol):
    async def create_payment(self, payment: Payment, return_url: str) -> str:
        """Возвращает URL, куда отправить владельца для оплаты."""
```

- **`StubProvider`** — дефолт для разработки. Возвращает ссылку на локальную
  страницу-имитацию платёжной формы с кнопкой подтверждения. Позволяет пройти
  весь сценарий без мерчант-аккаунта.
- **`YooKassaProvider`** — боевой. `POST /v3/payments` с Basic-авторизацией по
  `shop_id`/`secret_key` и заголовком `Idempotence-Key`, из ответа берётся
  `confirmation.confirmation_url`. Используется уже имеющийся `httpx`, новых
  зависимостей не требуется.

**Точка интеграции.** И подтверждение заглушки, и вебхук ЮKassa вызывают одну
функцию `apply_successful_payment(session, payment)`. Вся логика продления
живёт в ней одной; добавление третьего провайдера её не затронет.

**Арифметика продления:**

```
paid_until = max(сейчас, текущий paid_until или trial_ends_at) + 30 дней
status = ACTIVE
```

Оплата во время триала не сжигает остаток. Иначе выгоднее платить в последний
день, и это прямо провоцирует клиента тянуть до отключения.

**Истечение подписки не требует планировщика.** Никакой фоновой задачи,
переводящей статус в `expired`, не заводится: доступ определяется сравнением
дат в `subscription_is_usable`, и подписка перестаёт действовать ровно в момент,
когда `paid_until` оказывается в прошлом. Статус `EXPIRED` остаётся для случаев,
когда его выставляют явно. Это убирает из системы cron, который при отказе
молча раздавал бы бесплатный доступ.

**Вебхук ЮKassa** — `POST /webhooks/yookassa`. ЮKassa не подписывает
уведомления, поэтому телу запроса доверять нельзя: обработчик берёт из него
только идентификатор платежа и перезапрашивает статус через `GET
/v3/payments/{id}`. Продление происходит только если API подтвердил
`succeeded`. Обработчик идемпотентен — повторное уведомление по уже
проведённому платежу не продлевает подписку второй раз.

### Блокировка при неоплате

Единственная точка проверки — `process_update` в `app/services/bot_runtime.py`.
Туда уже загружается `Owner`, и мимо неё не проходит ни один апдейт бота. Если
подписка не активна, гостю уходит «Бот временно недоступен», обработка
прекращается.

Кабинет остаётся полностью доступен. Закрывать его нельзя: получится ловушка,
в которой владелец не может заплатить, потому что не заплатил. На дашборде
появляется баннер со ссылкой на оплату.

### Уведомления хозяину

Чтобы написать владельцу, нужен его `chat_id`, но собственного бота он может ни
разу не открывать. Связывание — через deep link.

В `Owner` добавляются `telegram_chat_id` и `link_code` (случайный, уникальный).
В кабинете появляется кнопка «Привязать Telegram», ведущая на
`t.me/<bot_username>?start=<link_code>`. Обработчик `/start` распознаёт
полезную нагрузку, сверяет код и сохраняет `chat_id`. Обычный `/start` без
кода продолжает работать как сценарий гостя.

При новой заявке владельцу уходит карточка с датами, объектом и контактом гостя
и кнопками «Подтвердить» / «Отклонить» (`booking:confirm:<id>` /
`booking:decline:<id>`).

**Обработчик callback обязан сверять `chat.id` с `owner.telegram_chat_id`.** Без
этой проверки любой гость, подобрав `callback_data`, подтвердит себе бронь —
идентификаторы бронирований последовательные, перебор тривиален.

После решения владельца уведомление уходит и гостю: `guest_telegram_id` уже
сохраняется при создании заявки.

Отправка уведомлений выносится в `app/services/notify.py` и не должна ронять
сценарий: если Telegram недоступен или владелец заблокировал бота, заявка всё
равно создаётся, ошибка пишется в лог.

### Загрузка фотографий

`POST /cabinet/units/{unit_id}/photos` принимает `UploadFile`:

- белый список типов — `image/jpeg`, `image/png`, `image/webp`;
- ограничение 5 МБ на файл и 10 фотографий на объект;
- имя файла генерируется как `uuid4`, расширение берётся из проверенного типа.
  Клиентское имя не используется никак — иначе открывается обход каталога через
  `../`;
- путь `uploads/units/<unit_id>/<uuid>.<ext>`, в базу пишется относительный
  путь, раздача идёт через уже настроенный `/media/`.

Добавляются удаление фотографии (с удалением файла с диска) и показ первой
фотографии гостю в боте при выборе объекта.

### Тесты

Инфраструктуры в проекте нет, заводится в рамках задачи: `pytest`,
`pytest-asyncio`, `httpx`, отдельная тестовая база, подмена зависимости
`get_db`.

| Файл | Что покрывает |
|------|---------------|
| `test_subscription.py` | арифметика продления, в том числе оплата во время триала; истёкшая подписка признаётся неактивной |
| `test_payments.py` | переходы статусов платежа, идемпотентность повторного уведомления |
| `test_bot_gate.py` | апдейт не обрабатывается при неактивной подписке |
| `test_notify.py` | чужой `chat_id` не может подтвердить бронь |

| `test_auth.py` | регистрация, логин, повторный email |
| `test_units.py` | создание объекта требует авторизации, чужой объект недоступен |

## Вне объёма

- **Автопродление подписки.** Списание по сохранённой карте — отдельная и
  заметно более тяжёлая история, включая хранение платёжного токена.
- **Градации тарифа** по числу объектов или функциям.
- **Возвраты и частичные платежи.**
- **Production-готовность** (TLS, шифрование токенов, Redis, бэкапы) — уже
  описана в `2026-09-23-production-hardening-design.md` и выполняется отдельно.

## Ограничение проверки

Код интеграции с ЮKassa невозможно проверить без зарегистрированного магазина и
боевых ключей. Тестами покрывается логика вокруг провайдера — состояния
платежа, продление, идемпотентность; сам обмен с ЮKassa проверяется заказчиком
после получения `shop_id` и `secret_key`. До этого момента рабочим провайдером
остаётся `stub`.
